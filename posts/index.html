Agent 的上下文是历史的视图，不是历史本身

2026年11月23日 · 7629 字 · 16 分钟

前两篇的 Agent 每一轮都把完整的消息历史发给模型。一次排查调用十几次工具，结果在历史里越积越多，最早的那些对当前判断已经没有用，却每一轮都要重新发一遍。

常见的做法是"历史太长就截掉前面的"，或者"太长就让模型总结一下"。两种做法都把历史和发给模型的上下文当成了同一个东西，所以压缩时总要在"省 token"和"丢信息"之间二选一。本文是「Agent 工程笔记」系列的第三篇，继续以 Go 实现的线上故障排查 Agent 为例，先把这两样东西分开，再讨论什么时候压缩、怎么压缩、哪些信息不能交给摘要，最后补上第一篇欠下的收尾轮。

Agent 的工具接口，读者是模型

2026年11月20日 · 6620 字 · 14 分钟

上一篇讲 Agent 循环时有一个前提：工具出错时，错误信息作为工具结果交给模型，由模型决定下一步。这句话把一个问题推给了工具层：如果工具返回的内容是给模型读的，那工具接口本身应该怎么设计？

大多数 Agent 的工具是把现有的内部 API 包一层：参数照搬，返回值照搬，错误照搬。这些 API 是为程序员设计的，而现在读者换成了模型。本文是「Agent 工程笔记」系列的第二篇，继续以 Go 实现的线上故障排查 Agent 为例，把一个照搬 API 的工具一步步改成为模型设计的工具。

从单体到微服务：复杂度的重新分布

2026年3月12日 · 4368 字 · 9 分钟

关于微服务的讨论，常常会落入一种过于简单的表述：单体系统复杂、微服务系统简单，因此随着业务增长，系统理应从单体自然演进到微服务。这个判断的问题，不在于它完全错误，而在于它忽略了一个更关键的事实: 微服务通常并不会消除复杂度，它更像是在重写复杂度的分布方式。

单体系统的复杂度往往集中在代码库内部，表现为模块耦合、发布风险、技术栈僵化以及协作冲突。微服务则试图把这些问题拆开，让团队围绕业务能力独立开发、独立部署、独立扩展。但拆分之后，复杂度并没有凭空消失，它只是从进程内调用、单库事务和单代码库协作，转移到了服务边界、网络时序、数据一致性、运行时治理以及组织协同之中。
